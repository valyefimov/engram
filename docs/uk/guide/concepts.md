# Основні поняття

## Записи пам’яті

Запис — невелика самодостатня нотатка, написана для майбутнього читача без контексту.

| Поле | Значення |
| --- | --- |
| `id` | Короткий і читабельний: `dec_k3x9q2mf`, `pit_…`, `pri_…` |
| `kind` | Що це (див. нижче) |
| `title` | Конкретний заголовок для пошуку — саме рішення, а не тема |
| `content` | Деталі й, головне, **обґрунтування** |
| `tags` | Теми в нижньому регістрі: `auth`, `db`, `payments` |
| `files` | Шляхи відносно репозиторію — для пошуку за файлами |
| `status` | `active`, `superseded`, `rejected` або `archived` |
| `importance` | 1 (дрібниця) … 5 (несуча конструкція) — впливає на ранжування й стиснення |
| `source` | `agent`, `user`, `adr:docs/adr/0003.md`, `git:…` |

### Види (kind)

| Вид | Для чого |
| --- | --- |
| `decision` | Архітектурний чи продуктовий вибір — або відхилений варіант (`status: rejected`) |
| `pitfall` | Граблі: що сталося, чому, як уникнути |
| `principle` | Правило, якого має дотримуватися кожна зміна |
| `fact` | Простий факт: «прод-БД — Postgres 16» |
| `discussion` | Суть обговорення: варіанти, аргументи, підсумок |
| `note` | Усе інше, що варто зберегти |
| `file` | Для чого модуль, якщо це неочевидно з коду |
| `session` | Підсумок робочої сесії |

### Дедуплікація під час запису

Агенти люблять «запам’ятовувати» одне й те саме двічі. Запис із тим самим видом і заголовком, що й активний, **оновлює** його (теги й файли об’єднуються, важливість береться максимальна).

## Статуси та історія

engram не перезаписує історію, коли ви передумали:

- **superseded** — замінено новішим записом. `supersede(old, new)` позначає старий і додає ребро `new —supersedes→ old`.
- **rejected** — варіант розглядали й відхилили. Саме це робить питання «чому не X?» таким, на яке можна відповісти.
- **archived** — м’яке видалення: приховано з пошуку, збережено для історії. Жорстке видалення залишає tombstone, щоб воно дійшло до колег.

За замовчуванням пошук показує лише `active`; `include_inactive` (або `--all`) — усе.

## Граф знань

Записи з’єднані типізованими напрямленими ребрами:

| Зв’язок | Читається як |
| --- | --- |
| `relates_to` | загальний зв’язок |
| `depends_on` | *from* правильне, лише поки правильне *to* |
| `implements` | *from* реалізує рішення / принцип *to* |
| `supersedes` | *from* замінило *to* |
| `rejected_because` | варіант *from* відхилено через *to* |
| `caused_by` | граблі *from* спричинені *to* |
| `part_of` | *from* — частина більшої теми *to* |

`engram_why` проходить по `supersedes`, `rejected_because` і `caused_by` та перетворює розрізнені записи на хронологію. `engram_related` ходить будь-якими ребрами в обидва боки.

## Сесії

`engram_session_start` відкриває сесію під мету й повертає контекст-пакет. `engram_session_end` зберігає підсумок — **зроблено / вирішено / відкрито / далі** — як запис `session`, який можна знайти. Контекст-пакет наступної сесії починається з нього.

## Контекст-пакет

Компресор контексту збирає брифінг під завдання в межах бюджету токенів (за замовчуванням 2000):

1. Збираються й пріоритизуються **принципи**, **граблі за темою завдання**, **релевантні записи**, **ключові рішення**.
2. Найпріоритетніше виводиться **повністю**.
3. Наступний рівень **стискається до одного рядка** (id + заголовок + теги).
4. Решта **відкидається** — і пакет повідомляє, скільки, щоб агент знав, що можна зробити `recall`.

## Пошук

Повнотекстовий пошук — SQLite FTS5 з ранжуванням BM25 (заголовок ≫ теги > вміст > файли), стемінгом Porter і Unicode-токенізацією — працює англійською, українською, російською та іншими мовами. Потім рахунок посилюється за видом, важливістю, статусом і свіжістю. Запити поблажливі: терміни об’єднуються через OR, довгі шукаються за префіксом — «auth» знайде «authentication».
